# หลักการทำงานใน studio

หลักคิดที่ใช้กับ **ทุกงาน** (กฎเฉพาะเรื่องอยู่ใน `guardrails.md`, หลักลงทุนอยู่ใน `research/PHILOSOPHY.md`).
ใช้โดย `/reflect`, `/meditate`, `/ruminate` เพื่อตัดสินว่าบทเรียนควรไปอยู่ที่ไหน.

## 1. ฝังบทเรียนในโครงสร้าง อย่าแค่จดไว้
คำสั่งที่เป็นตัวหนังสือ (memory, CLAUDE.md) ต้องอาศัยให้ AI เห็น จำ และทำตาม — พลาดได้ทุกขั้น.
โค้ด/สคริปต์/hook บังคับเองโดยไม่ต้องจำ.

ลำดับความชอบ: **แก้สคริปต์ให้ทำถูกเอง → แก้ skill/agent → hook อัตโนมัติ → memory** (ทางสุดท้าย).
- ✅ รูป HEIC ถูกเก็บแบบหมุน → ใส่ `ImageOps.exif_transpose` ในสคริปต์ ไม่ใช่จด "อย่าลืมหมุนรูป"
- ✅ archivist ลบ `node_modules` ของ cobalt แล้ว cobalt พัง → แก้กฎใน `archivist.md` ให้ยกเว้น `api/`
- เมื่อไหร่ที่กำลังจะเขียนคำเตือนเดิมเป็นครั้งที่ 2 = สัญญาณว่าต้องฝังเป็นโครงสร้างแล้ว

## 2. แก้ที่ต้นเหตุ
อาการกับสาเหตุคนละอย่าง. ลองวิธีใหม่ทีละอันโดยไม่รู้ว่าทำไมพัง = เสียรอบ.
- ✅ MLX hallucinate บนเสียงยาว → ต้นเหตุคือช่วงเงียบ/เสียงดนตรี → ตัดด้วย VAD ก่อน (ไม่ใช่แค่สลับโมเดล 3 รอบ)
- ✅ FB course โหลดได้วิดีโอผิดตอน → ต้นเหตุคือหน้าเว็บ prefetch ทุกตอนพร้อมกัน → จับ manifest ของตอนที่เล่นจริง
- ก่อนลองวิธีที่ 2 ให้ตอบได้ก่อนว่า **วิธีที่ 1 พังเพราะอะไร**
- **สงสัย state ก่อนสงสัยโค้ด** (poteto/noodle `debugging`, `oops`): ของที่เคยใช้ได้แล้วพัง ไล่ตามลำดับ
  ไฟล์ state (cookie, token, session, ไฟล์ล็อก, cache) → environment (PATH, เวอร์ชัน python/ffmpeg, เน็ต) → config (plist, .env) → **ค่อยดูโค้ด**
- แก้แล้ว grep หาจุดเดียวกันที่อื่นด้วย — บั๊กแบบเดียวกันมักซ้ำหลายที่

## 3. ใช้ usage อย่างรู้ราคา
ผู้ใช้ซีเรียสเรื่อง usage. ทุก agent/รอบ/การรอ มีต้นทุน.
- **Opus วางแผน, Sonnet ลงมือ, Haiku งานกลไก** — เลือก model ต่ำสุดที่พอ
- งานยาว (>5 นาที) → แสดงแผนให้ผู้ใช้ confirm ก่อน
- **รองานเบื้องหลัง = รอ notification ห้าม poll ซ้ำ** (เคยพิมพ์ "I'll wait for the Monitor" วนหลายสิบรอบใน session เดียว)
- ส่ง context ให้ subagent ครบตั้งแต่แรก — prompt ยาวขึ้น 1 ครั้ง ถูกกว่าให้มันค้นใหม่หลายรอบ

## 4. ปกป้อง context window
context ที่ใช้ไปแล้วเอาคืนไม่ได้ใน session.
- อย่าอ่านไฟล์ใหญ่ทั้งไฟล์ถ้าต้องการแค่ส่วนเดียว (เช่น KB → อ่านผ่าน `KNOWLEDGE_INDEX.md`)
- ผลลัพธ์ยาว (log, transcript ดิบ, ภาพ) → ย่อด้วยสคริปต์หรือส่ง subagent สรุปกลับมา
- ภาพตรวจงาน → crop เฉพาะจุดที่ต้องดู แทนส่งภาพเต็ม

## 5. พิสูจน์ว่าใช้ได้จริง ก่อนบอกว่าเสร็จ
"รันผ่าน" ≠ "ได้ผลถูก".
- ✅ ลบคนออกจากรูป → crop ดู before/after ทุกจุดที่แก้ (เจอกลีบกุหลาบเลอะ จึงแก้ทัน)
- ✅ ย่อวิดีโอ → เทียบเฟรมเดียวกันของไฟล์เก่า/ใหม่ก่อนเขียนทับ
- ✅ บอท launchd → verify ด้วย `launchctl kickstart` ไม่ใช่รันมือใน terminal (ดู `guardrails.md`)
- ทดสอบไม่ได้ → บอกผู้ใช้ตรงๆ ว่ายังไม่ได้ verify ส่วนไหน

**เกณฑ์หลักฐาน (proof bar — จาก poteto/verification-skill-example, prove-it-works):**
- **เชื่อผลงาน ไม่ใช่คำรายงาน** — งานที่ส่ง agent ทำ ให้เปิดไฟล์/ภาพ/ผลลัพธ์จริงดูเอง อย่าเชื่อสรุปของ agent (agent รายงานสิ่งที่ตั้งใจทำ ไม่ใช่สิ่งที่เกิดจริงเสมอไป)
- **ดูของจริง ไม่ใช่ตัวแทน** — เวลาแก้ไฟล์ล่าสุด, log ว่า "done", screenshot เก่า ไม่นับเป็นหลักฐาน; อ่านค่าจริง/เปิดผลจริง. ตรวจแล้วผลแปลก → สงสัยวิธีตรวจก่อนสงสัยระบบ
- **เช็คความสดก่อน** — ทดสอบกับไฟล์เก่า/cache/บอทตัวที่ยังไม่ reload ไม่นับ
- **ครบทุกเส้นทางที่งานกระทบ** — ตอนสำเร็จ, ตอน error, ตอนไม่มีข้อมูล (เช่น "ไม่มีโพสต์ใหม่" ต้องแยกให้ออกจาก "ดึงข้อมูลไม่ได้"); ส่วนไหนตรวจไม่ได้ → บอกชื่อ + เหตุผล

# How

ต้นแบบ: poteto/how (MIT) — ปรับให้ประหยัด usage และตอบเป็นภาษาไทย.
ผู้อ่านคือเจ้าของ studio (นักลงทุน ไม่ใช่โปรแกรมเมอร์) — ต้องเข้าใจพอจะตัดสินใจและสั่งงานต่อได้ ไม่ใช่อ่านโค้ดแทน.

## 1. ตีความคำถาม แล้วประเมินขนาด
ไม่ชัดว่าหมายถึงอะไร → เดาที่สมเหตุสมผลที่สุด บอกว่าตีความแบบไหน แล้วลุยเลย (ผู้ใช้แก้ทีหลังได้).

**จุดเริ่มค้นในเครื่องนี้:**
- บอท launchd: `ls ~/Library/LaunchAgents/com.alonsi.*` → plist บอกสคริปต์ + เวลา; คู่มือรายบอท `guides/bots/`
- skill/agent/command: `.claude/skills/`, `.claude/agents/`, `.claude/commands/`, `~/.claude/skills/`
- สคริปต์: `tools/`, `stock-research/`, `projects/<ชื่อ>/`
- กฎ/บทเรียน: `guides/guardrails.md`, `guides/principles.md`, memory

| ขนาด | ตัวอย่าง | วิธี |
|---|---|---|
| **เล็ก** | ฟังก์ชันเดียว, skill ตัวเดียว, บอทตัวเดียว | อ่านเองใน context นี้ แล้วเขียนคำตอบ |
| **ใหญ่** | ระบบหลายส่วน (digest ทั้งชุด, learn-session ทั้ง pipeline) | แตก 2–4 มุมที่ไม่ซ้ำกัน → ส่ง `Explore` agent (`model: haiku`, read-only) มุมละตัว **ใน message เดียว** → รวมผลเองใน context นี้ (ไม่ spawn ตัวเขียนแยก) |

ไม่แน่ใจ → เลือกแบบเล็กก่อน ค่อยขยายถ้าติด.

**Prompt ของ Explore แต่ละตัวต้องมี:** คำถาม, มุมที่รับผิดชอบ, จุดเริ่มค้นข้างบน, และให้คืนผลเป็น:
ส่วนประกอบที่เจอ (ชื่อ + path + ทำอะไร 1 ประโยค) / ลำดับการทำงานจากจุดเริ่มถึงผลลัพธ์ / ไฟล์ที่อ่าน / จุดเชื่อมกับระบบอื่น / สิ่งที่ไม่ชัดเจนหรือน่าแปลกใจ / **คำถามที่ตอบไม่ได้ (บอกตรงๆ ห้ามแต่ง)**

## 2. กติกาการค้น (ทั้งทำเองและ Explore)
- เปิดอ่านโค้ดจริง — ห้ามสรุปจากชื่อไฟล์หรือคอมเมนต์อย่างเดียว
- ไล่จากจุดเริ่ม (อะไรสั่งให้มันทำงาน: เวลา launchd, คำสั่งผู้ใช้, hook) → ทำอะไรต่อ → ข้อมูลไปไหน → ผลลัพธ์ออกที่ไหน (LINE, Notion, ไฟล์)
- หยุดเมื่ออธิบายได้ครบทางโดยไม่ต้องโบกมือข้าม
- ตามหาสิ่งที่คนใหม่จะเข้าใจผิด (เช่น รันมือผ่านแต่ launchd พัง — `guides/guardrails.md`)

## 3. เขียนคำตอบ (ภาษาไทย)
ใช้โครงนี้ ตัดหัวข้อที่ไม่จำเป็นได้:

**ภาพรวม** — 2–3 ประโยค: มันคืออะไร ทำไปทำไม. อ่านแค่นี้ต้องรู้ว่าต้องอ่านต่อไหม
**ส่วนประกอบหลัก** — เฉพาะที่ต้องรู้เพื่อเข้าใจส่วนที่เหลือ อธิบายสั้นๆ
**ทำงานยังไง** — ส่วนหลัก: เริ่มจากอะไร → ทีละขั้น → ข้อมูลไปไหน → จุดที่ต้องตัดสินใจ. ร้อยแก้ว ไม่ใช่ pseudocode. ถ้ามีหลายส่วนคุยกันใช้แผนภาพ (mermaid หรือ ASCII) เมื่อช่วยให้เข้าใจจริงเท่านั้น
**ไฟล์อยู่ไหน** — แผนที่สั้นๆ เฉพาะไฟล์ที่ต้องเปิดถ้าจะแก้
**จุดที่มักพลาด** — สิ่งที่ไม่ตรงไปตรงมา, ประวัติที่อธิบายว่าทำไมหน้าตาแปลก, จุดเปราะ
**ยังไม่รู้** — คำถามที่ค้นแล้วตอบไม่ได้ (ถ้ามี)

สไตล์: พูดถึงของจริง ("`digest_watchdog.py` เช็คไฟล์ log ทุก 09:00") ไม่ใช่นามธรรม ("ระบบตรวจสอบสถานะ"); ศัพท์เทคนิคแปลไทยครั้งแรกที่เจอ; อุปมาเฉพาะเมื่อช่วยจริง.

## 4. โหมดวิจารณ์ (เมื่อผู้ใช้ขอ "มีจุดอ่อนไหม", "ควรปรับอะไร", "ทำไมพังบ่อย")
อธิบายให้จบก่อน (ข้อ 1–3) แล้วอ่านโค้ดอีกรอบผ่าน 3 มุม **ใน context นี้**:
1. **เงียบตาย** — พังแล้วจะมีใครรู้ไหม (log, แจ้งเตือน, watchdog)? token/session หมดอายุแล้วเกิดอะไร?
2. **ต้นทุน** — เรียก LLM/API มากเกินจำเป็นไหม, ทำงานซ้ำไหม, ใช้โมเดลแพงเกินงาน
3. **เปราะต่อการเปลี่ยน** — path/เวอร์ชัน Python/รูปแบบเว็บที่ hard-code, พึ่งพา session login

ทุกข้อที่เจอต้องมี **หลักฐาน (ไฟล์:บรรทัด)** และ **ผลกระทบจริง**. ไม่มีหลักฐาน = ไม่ใช่ข้อค้นพบ. ไม่เจออะไร = ตอบว่าไม่เจอ ได้.
ตัดสินแบบบรรณาธิการ: **ต้องแก้ / น่าพิจารณา / รับทราบ / ตัดทิ้ง** — นำเสนอคำอธิบายก่อน แล้วค่อยต่อด้วยผลวิจารณ์ (คนที่แค่อยากเข้าใจจะได้ไม่ต้องอ่านผลวิจารณ์).
ถ้าจะแก้ → เป็นงานแยก ทำตามกฎวางแผนก่อนลงมือ.
